# Scheduling and free Bumps

## Persistent work

Use the environment's actual automation tool/schema if persistent scheduling exists. Do not substitute a long sleep, background daemon, chat promise or raw directive. Reuse an existing job for the same purpose and inspect its prompt, timezone, schedule and notification policy before edits. Keep one shop's send/spend authority isolated.

Agree on working hours, cadence, report time and alerts. Hourly checks during staffed hours, a morning summary and a Monday report are examples, not platform limits. Do not schedule a reminder merely because the owner says they will check something tomorrow.

Read actual local date/time at each run, including delayed triggers. Scheduled, attempted, verified, skipped and missed are different outcomes. If access fails, report the blocker rather than assuming no customer activity.

## Native free eligibility

Verify this account/market's current simultaneous slots, cooldowns and terminology. Some interfaces offer More → Bump Now near a paid Boost button. Inspect the actual flow; stop before unapproved funding, top-up or campaign creation. Names do not establish price.

Record verified limits with source/date privately. A simultaneous-slot limit is not a daily allowance. A cooldown can permit reuse, but does not guarantee unlimited reach or ranking.

For setup, adapt [the recurring-job prompts](recurring-job-prompts.md) to the owner's actual operating file and host scheduler. Prompts do not create authorisation or a running job by themselves.

Before a round:

1. Read owner's priorities, selection authority, working window and execution ledger.
2. Verify exact IDs, units, stock, free eligibility and active Bumps.
3. Capture selected-product metrics with period, cutoff, order type, traffic source and N/A fields.
4. Execute only verified free actions; do not displace unrelated active items or change price/cover mid-test without authority.
5. Immediately log each verified start/countdown, approximate expiry and evidence. A later countdown screenshot cannot prove an exact earlier start.

Choose candidates from verified contribution, stock readiness, actual buying interest and a defined test. Preserve mandatory priorities. Goods margin alone is not net profit; a test order is not conversion evidence.

## Timing, retries and failures

Use observed expiry plus a buffer, not fixed wall-clock resets. Allow time for all actions and normal scheduler jitter inside the owner's approved window. Avoid a final round that leaves seconds after cooldown.

Worked timing example, not a platform default: with a verified four-hour cooldown and a strict 08:00–20:00 working window, sequential clicks and reporting delay make four complete five-item rounds fragile or impossible. Three spaced rounds may be the honest plan. Do not promise four by multiplying capacity; ask about a longer window only if the owner wants that trade-off.

When a retry is authorised, allow one bounded retry for missing targets, reusing the one-off job. Skip verified successes. Do not multiply jobs, restart successful Bumps or silently extend a deadline. A delayed run starting after its deadline is missed, not complete.

If there is insufficient time, log partial/missed work, remove the obsolete one-off and notify once when material. Propose a less fragile future schedule within scope. Keep the main recurring job; remove completed/obsolete/wrong-date one-offs. Actual daily count comes from successful records, not slots times scheduled rounds.

## Monitoring and outcomes

Check all authorised shop orders/chats, not only promoted items. Keep test exclusions and alert deduplication across runs. Customer sends have their own eligibility checks.

Stay quiet on unchanged state unless a periodic report was requested. Notify actionable orders, customer messages, completed replies, access failures, approaching deadlines or material missed rounds. A timer firing is not news.

Compare compatible windows and actual units bought. Report raw impressions, clicks, visitors, carts and genuine orders where available. Rolling-count changes are not Bump causality; one order is not a proven winner. Read the analysis reference for decisions.
